# وضعیت پروژه

آخرین بررسی: ۲۱ اکتبر ۲۰۲۶. خروجی اول بخش ۱۹ و بازطراحی مستقل رابط با الهام از Metronic 8 Demo 1 پیاده‌سازی و آزمون شده‌اند. این به‌معنای تکمیل تمام مراحل نسخه اول نیست.

## ترتیب منوها برای تست اطلاعات پایه

۲۱ اکتبر ۲۰۲۶: گروه «اطلاعات پایه» بلافاصله بعد از «پرونده هنرجویان» قرار گرفت؛ ترتیب گروه‌ها اکنون کارهای امروز، پرونده هنرجویان، اطلاعات پایه، امور مالی، قوانین و مدارک، گزارش‌ها و مدیریت است. زیرمنوهای مرتبط در گروه فعلی خود باقی‌اند؛ رفتار باز و بسته شدن و محدودیت دسترسی حفظ شده است. `npm run build` موفق است؛ نسخه ساخته‌شده از سرور محلی موجود ارائه می‌شود.

## درخواست جاری: تب‌های هنرجو و وضعیت جلسات ترم

تاریخ بررسی: ۲۱ اکتبر ۲۰۲۶. خطای «بخش اطلاعات پایه یافت نشد» تصویر کاربر از اجرای بک‌اند قدیمی بود؛ سرور پورت ۳۰۰۰ با API و migration 005 راه‌اندازی شد. صفحه «اطلاعات پایه ← وضعیت جلسات ترم» اکنون چهار رکورد واقعی حاضر، غایب، رزرو و کنسل دارد؛ فهرست AG Grid، فیلتر/مرتب‌سازی سروری و ویرایش مستقل عنوان و توضیحات فعال‌اند. چهار کد، فعال بودن آن‌ها و قواعد مصرف سهم ثابت‌اند؛ افزودن/حذف یا تغییر کد پشتیبانی نمی‌شود. عنوان فارسی در ابتدای گرید قرار گرفت تا در موبایل قبل از کد انگلیسی دیده شود. سلول وضعیت ردیف‌های بارگذاری دیگر `undefined` نشان نمی‌دهد.

سن اختیاری (عدد صحیح صفر تا ۱۳۰) و آدرس (حداکثر ۲۰۰۰ نویسه) به ایجاد/ویرایش و دیتابیس هنرجو افزوده شدند. PATCH قدیمی مقادیر را حفظ می‌کند و خالی‌کردن صریح ممکن است. پاسخ حسابدار اطلاعات شخصی جدید را افشا نمی‌کند. فرم هنرجو چهار تب دارد: اطلاعات فردی؛ اطلاعات ساز و جلسه؛ حضور و غیاب؛ مالی. پیش‌نویس اطلاعات فردی و عکس با جابه‌جایی تب از بین نمی‌رود. در ایجاد، ابتدا پرونده و واحد آموزشی ذخیره می‌شود؛ سپس عملیات ترم/جلسه/شهریه در تب‌ها قابل استفاده‌اند. تب مالی فقط برای نقش دارای دسترسی مالی نمایش داده می‌شود.

جلسات هر ترم و جدول حضور و غیاب برای هر جلسه چهار radio واقعی دارند. حاضر/رزرو با کنترل نسخه و ظرفیت در سرور ذخیره می‌شوند؛ غایب فرم تصمیم صریح کسر سهم و دلیل را باز می‌کند؛ کنسل دلیل و لغوکننده می‌خواهد. تغییر نام وضعیت در اطلاعات پایه در radioها، انتخاب‌گر فرم و نشان/فیلتر وضعیت جدول پرونده خوانده می‌شود. پرداخت، صورتحساب، سهم جلسات و تمدید قبلی حفظ شده‌اند. ظاهر لیبل ثابت، ورودی sm، Select2 و گرید طوسی/سفید باقی است.

اعتبارسنجی: `npm run check` و `npm run build` موفق؛ **۲۶ تست API موفق**، شامل ماندگاری سن/آدرس، اعتبارسنجی و حریم خصوصی و چهار وضعیت ثابت، کنترل نسخه و دسترسی. **۴۶ تست Chrome موفق در ۱٫۴ دقیقه** روی دسکتاپ و Pixel 7 شبیه‌سازی‌شده: کل مسیر ثبت تا تمدید/پرداخت، تب‌ها، حفظ پیش‌نویس، تغییر واقعی حضور به غیبت، ویرایش وضعیت، عکس، سوییچ و Select2 بررسی شدند. پس از اصلاح ترتیب ستون موبایل و یکسان‌سازی عنوان وضعیت‌ها، ۶ تست تکمیلی موفق اجرا شد. تصاویر واقعی [وضعیت‌ها دسکتاپ](evidence/desktop-session-statuses.png)، [موبایل](evidence/mobile-session-statuses.png)، [اطلاعات فردی](evidence/desktop-student-tab-personal.png) و [حضور و غیاب موبایل](evidence/mobile-student-tab-attendance.png) باز و بصری بررسی شدند؛ هم‌پوشانی یا سرریز صفحه دیده نشد. ستون‌های بیشتر گرید در موبایل با اسکرول افقی داخلی در دسترس‌اند. موبایل فیزیکی بررسی نشده است.

اجرا: `npm ci` برای نصب تازه، سپس `npm run build` و `APP_ORIGIN=http://localhost:3000 npm run api`؛ ایجاد مدیر و متغیرهای محیطی طبق README. سرور هنگام شروع migration را خودکار اجرا می‌کند. پیش از ارتقای دیتابیس موجود بکاپ `data/backups/before-student-tabs-20261020.sqlite` گرفته شد؛ داده تمام ستون‌های قبلی هنرجو با بکاپ برابر و `integrity_check=ok` است؛ اطلاعات نمایشی آزمایشی وارد دیتابیس واقعی نشدند. صفحه جاری Chrome را برای دریافت build تازه refresh کنید.

باقی‌مانده: برای این درخواست نقص عملکردی شناخته‌شده‌ای ثبت نشده؛ سامانه فعلی نقش‌های مدیر، منشی و حسابدار دارد و حساب ورود مستقل مدرس هنوز جزو مدیریت دسترسی پیاده‌شده نیست. حضور و غیاب فعلاً با دسترسی آموزشی موجود انجام می‌شود. صفحات سایر مراحل بریف که «در انتظار پیاده‌سازی» هستند همچنان باقی‌اند؛ تکمیل این درخواست به‌معنای تکمیل تمام پروژه نیست. پوش روی ریموت Git انجام می‌شود؛ میزبان انتشار عمومی جداگانه تعریف نشده است.

## سابقه: نام انگلیسی ساز

فیلد اختیاری «نام انگلیسی ساز» با جهت LTR، اندازه sm و لیبل ثابت به ایجاد و ویرایش ساز اضافه شد؛ در AG Grid هم ستون مستقل با فیلتر/مرتب‌سازی سروری دارد. پاسخ API فیلد `english_name` و درخواست ایجاد/ویرایش `englishName` دارد. مقدار حداکثر ۱۵۰ نویسه است؛ خالی‌کردن صریح پشتیبانی می‌شود و PATCH قدیمی که این فیلد را نمی‌فرستد مقدار قبلی را حفظ می‌کند. فهرست‌های نوع تدریس و مدرسین تغییر فیلد ندارند.

migration 004 ستون متنی با مقدار پیش‌فرض خالی می‌افزاید؛ ترجمه ساختگی برای رکوردهای قبلی ساخته نمی‌شود. قبل از اجرا بکاپ سازگار در `data/backups/before-instrument-english-20261020.sqlite` گرفته شد. سرور پورت ۳۰۰۰ با کد جدید راه‌اندازی شد؛ migration=4، مشخصات/وضعیت/نسخه سازهای قبلی با بکاپ برابر و integrity_check=ok است. اجرا همان `npm run build` و `APP_ORIGIN=http://localhost:3000 npm run api` است.

build موفق؛ **۲۴ تست API موفق** شامل ایجاد، ویرایش، حفظ مقدار در PATCH قدیمی، فیلتر انگلیسی، محدودیت طول و حذف مقدار. **۱۰ تست Chrome اطلاعات پایه در ۱۶٫۰ ثانیه موفق**؛ ذخیره Violin، ویرایش به Piano و بازخوانی آن روی دسکتاپ و موبایل بررسی شد. تصاویر [دسکتاپ](evidence/desktop-instrument-english-name.png) و [موبایل](evidence/mobile-instrument-english-name.png) باز و بصری بررسی شدند؛ تداخل و سرریز دیده نشد. مورد عملکردی شناخته‌شده‌ای برای این درخواست باقی نیست.

## سابقه: حذف Floating Label، ورودی sm و سوییچ

طبق تصمیم جدید کاربر، عنوان تمام فرم‌ها از حالت شناور خارج و ثابت، قابل کلیک و بالای فیلد قرار گرفت. این تصمیم جای الزام قدیمی Floating Label بریف را می‌گیرد. Field مشترک، CSS همه فرم‌ها و Select2 تغییر کردند: input/select ارتفاع ۳۸ پیکسل، padding کوچک و فونت ۱۲؛ textarea ارتفاع پایه ۸۸ دارد. عنوان هنگام فوکوس، مقدار، select غیرفعال و صفر جابه‌جا نمی‌شود. این استاندارد در AGENTS.md و README ثبت شد؛ فیلترهای خود AG Grid با Floating Filter اشتباه گرفته نمی‌شوند و داخل گرید باقی‌اند.

سوییچ مشترک با ControlValueAccessor، role=switch، لیبل، فوکوس و Space، حالت checked و disabled واقعی ساخته شد. وضعیت فعال/غیرفعال اطلاعات پایه سوییچی است. برای حفظ هر سه وضعیت هنرجو، سوییچ فعال بودن و سوییچ جداگانه بایگانی قرار دارد؛ خروج از بایگانی پرونده را غیرفعال نگه می‌دارد تا فعال‌سازی صریح باشد. وضعیت کارکنان در گرید سوییچ واقعی دارد؛ تأیید قبلی، پایان نشست و ممنوعیت غیرفعال‌سازی آخرین مدیر حفظ‌اند و لغو/خطا سوییچ را برمی‌گرداند. برای بولین کسر سهم غیبت هم سوییچ وجود دارد؛ مقدار اولیه هنوز «تعیین نشده» است و انتخاب/تأیید صریح لازم است. حالت خاموش اولیه خودکار تصمیم مالی/آموزشی نمی‌شود. وضعیت چندحالته حضور و غیاب و enumهای آموزشی با Select2 باقی‌اند.

مرجع کاربر [صفحه امنیت Demo 1](https://preview.keenthemes.com/metronic8/demo1/?page=account/security) و تصاویر ضمیمه بررسی شدند؛ سوییچ آبی/خاکستری و دایره سفید با CSS مستقل ساخته شد. فرم، API، دیتابیس و محدودیت‌های دسترسی حفظ شدند و migration تازه لازم نبود.

بررسی نهایی: `npm run check` و `npm run build` موفق؛ **۲۳ تست API موفق**. **۴۲ تست Chrome موفق در حدود ۱٫۳ دقیقه** روی دسکتاپ و Pixel 7 شبیه‌سازی‌شده؛ لیبل ثابت و فاصله از کنترل، ارتفاع ۳۸، انتخاب با کیبورد، ذخیره/بازخوانی فعال و بایگانی، تغییر واقعی وضعیت کارکنان، لغو تأیید و حفاظت آخرین مدیر بررسی شدند. مسیر کامل هنرجو تا تمدید، اطلاعات پایه، Select2 و عملیات ردیف همچنان موفق‌اند. بررسی تصویری تکمیلی پس از پایان transition با **۱۴ تست موفق در ۲۰ ثانیه** انجام شد. تصاویر واقعی [فرم دسکتاپ](evidence/desktop-compact-switches.png)، [موبایل](evidence/mobile-compact-switches.png)، [مدرس دسکتاپ](evidence/desktop-compact-instructors.png) و [موبایل](evidence/mobile-compact-instructors.png) باز و بصری بررسی شدند؛ هم‌پوشانی یا بریدگی دیده نشد. دستگاه فیزیکی آزمایش نشده است.

اجرا: `npm ci` برای نصب تازه، سپس `npm run build` و `APP_ORIGIN=http://localhost:3000 npm run api`؛ تنظیم env و ساخت مدیر طبق README. سرور محلی موجود همان build جدید را ارائه می‌کند. داده و فایل محیطی طبق .gitignore وارد Git نمی‌شوند. ریموت بررسی‌شده origin روی GitHub و شاخه تحویل main است؛ چون ریموت تا این مرحله تنها README اولیه داشت، کد کامل فعلی پروژه و مستندات هم در تحویل Git قرار می‌گیرند. در این درخواست راه‌اندازی میزبان عمومی تازه تعریف نشده است. برای لیبل/sm/سوییچ مورد عملکردی شناخته‌شده‌ای باقی نیست؛ باقی‌مانده کل دامنه و PWA در انتهای فایل آمده است.

## سابقه: حذف منوی مستقل آموزش

طبق اصلاح صریح کاربر، گروه «آموزش» و سه زیرمنوی «کلاس‌ها و گروه‌ها»، «ترم‌ها و تمدید» و «جلسات و حضور و غیاب» از سایدبار حذف شدند. این تصمیم جای الزام قبلی بریف به نگهداری این ورودی‌های سراسری را برای چیدمان فعلی می‌گیرد. عملیات ترم/تمدید، ثبت جلسه و حضور و غیاب از مدیریت هنرجویان، ستون عملیات و پرونده همان هنرجو ادامه دارند؛ قابلیت و داده‌ای حذف نشد. گروه اطلاعات پایه و سایر منوها باقی‌اند؛ در حال حاضر پنج گروه آکاردئونی داریم.

صفحات placeholder این سه مقصد دیگر ساخته نمی‌شوند؛ لینک‌های قدیمی `/classes`، `/terms` و `/sessions` به `/students` هدایت می‌شوند. routeهای API آموزش و عملیات واقعی پرونده تغییری نکردند. این تصمیم در AGENTS.md ثبت شد تا منوی حذف‌شده دوباره برنگردد. build و strict check موفق‌اند. اجرای نسخه مانند قبل: `npm run build` و `APP_ORIGIN=http://localhost:3000 npm run api`؛ سرور فعال همان build جدید را ارائه می‌کند. برای این درخواست مورد عملکردی شناخته‌شده‌ای باقی نیست.

تشخیص گزینه فعال نیز اصلاح شد: فیلتر/شماره صفحه در query مانع highlight منو نیست و صفحه ثبت/ویرایش اطلاعات پایه زیر منوی همان فهرست فعال می‌ماند؛ مسیرهای هم‌پوشان تنظیمات همچنان فقط گزینه دقیق خود را فعال می‌کنند.

نتیجه نهایی: **۳۸ تست Chrome در حدود ۱٫۲ دقیقه موفق**؛ نبود گروه/سه زیرمنوی حذف‌شده، هدایت هر سه آدرس قدیمی، باز/بسته‌شدن گروه‌های باقی‌مانده و مسیر کامل آموزش داخل پرونده تا تمدید در دسکتاپ و موبایل بررسی شدند. وضعیت فعال منو با query صفحه‌بندی و پس از refresh نیز تأیید شد. تصاویر [دسکتاپ](evidence/desktop-student-centered-menu.png) و [موبایل](evidence/mobile-student-centered-menu.png) باز و بصری بررسی شدند. این تغییر نیازی به migration یا تغییر API نداشت.

## سابقه: اطلاعات پایه — نوع تدریس، مدرسین و سازها

سه زیرمنوی واقعی به گروه آکاردئونی «اطلاعات پایه» اضافه شدند: **نوع تدریس، مدرسین، سازها**. کاربر در پاسخ به سؤال دامنه تأیید کرد که «نوع تدریس» فهرستی مستقل با عنوان دلخواه است؛ این فهرست جای حضوری/آنلاین یا خصوصی/گروهی را نمی‌گیرد. سازها هم از واحدهای آموزشی موجود (که سلفژ و کنترپوان را نیز شامل می‌شوند) جدا هستند. مسیرها `/base-data/teaching-types`، `/base-data/instructors` و `/base-data/instruments` است؛ هرکدام مسیر `/new` و `/:id/edit` دارند.

لیست‌ها از DataGrid مشترک و AG Grid سفید/طوسی، دانا و RTL استفاده می‌کنند؛ فیلتر فقط داخل ستون‌هاست. مرتب‌سازی، فیلتر کل داده و دریافت بلوکی/صفحه‌بندی در SQLite سرور انجام می‌شود. فیلتر/مرتب‌سازی/اندازه و شماره صفحه در URL می‌مانند و پس از ویرایش یا انصراف و refresh بازیابی می‌شوند. ستون عملیات دکمه ویرایش همان رکورد دارد. فرم مستقل مانند ساختار هنرجو، بخش اصلی و کارت وضعیت و نوار ذخیره/انصراف دارد؛ label شناور و Select2 واقعی حفظ شدند.

فیلدهای فعلی: عنوان/نام، توضیحات و وضعیت فعال/غیرفعال برای هر سه؛ مدرس شماره تماس اختیاری هم دارد. عنوان الزامی و حداکثر ۱۵۰ نویسه، توضیحات حداکثر ۲۰۰۰ است. عنوان تکراری نرمال‌شده برای ساز و نوع تدریس رد می‌شود؛ مدرس هم‌نام مجاز است. نسخه رکورد جلوی بازنویسی هم‌زمان را می‌گیرد. حذف دائمی وجود ندارد؛ غیرفعال‌سازی از فرم انجام می‌شود. مدیر و منشی مجازند؛ حسابدار در منو، route و تمام متدهای API منع می‌شود. مدرس به‌صورت خودکار حساب ورود ندارد.

APIهای GET فهرست، GET رکورد، POST و PATCH در `/api/base-data/:resource` واقعی‌اند؛ نام جدول و ستون از allowlist سرور، مقادیر پارامتری و write همراه audit/تراکنش است. migration **003_base_data.sql** سه جدول را بدون تغییر داده قبلی اضافه می‌کند. نوع تدریس دلخواه و مدرس/ساز در این مرحله فهرست‌های مستقل‌اند؛ انتخاب آن‌ها در فرم کلاس/ترم به بازطراحی همان فرم‌ها در مرحله بعد تعلق دارد. شیوه برگزاری و مدرس/مسیرهای آموزشی سوابق موجود تغییر نکرده‌اند. مدیریت «واحدهای آموزشی» و «آموزشگاه‌های دیگر» همچنان مقصدهای قبلی منتظر پیاده‌سازی‌اند.

فیلتر select ترم بیرون حضور و غیاب نیز حذف شد؛ تمام جلسات پرونده در یک گرید با ستون ترم قابل فیلتر قرار دارند. مسیرهای مستقیم حضور/ترم و عملیات همان رکورد حفظ شده‌اند. رنگ کرم/قهوه‌ای/سبز اورنزا از تم گرید، سرستون، حاشیه، آیکون، popup و hover حذف و سفید/طوسی خنثی جایگزین شد. badgeهای وضعیت معنا و رنگ عملیاتی دارند. فونت دانا و AG Grid باقی‌اند.

این تصمیم جای رنگ‌بندی قبلی اورنزا و هر فیلتر بیرونی را می‌گیرد. `npm run check` و build موفق‌اند؛ `npm test`: ۱۵ موفق. **Chrome: ۱۴ تست موفق در ۳۹٫۵ ثانیه، خروج صفر**؛ نبود کنترل بیرونی، جست‌وجو از Floating Filter، منوی پیشرفته داخل ردیف فیلتر، صفحه‌بندی و بازیابی URL، فیلتر ترم در خود گرید حضور و غیاب و تم سفید بررسی شدند. تصاویر دسکتاپ و موبایل باز و بصری بررسی شدند: [هنرجویان](evidence/desktop-ag-grid.png)، [موبایل](evidence/mobile-ag-grid.png)، [فیلتر ترم](evidence/desktop-attendance-filters.png). production build برابر 797.82 kB خام / 137.84 kB انتقال اولیه است. سرور واقعی با کد جست‌وجوی جدید و همان دیتابیس دوباره اجرا شد و نسخه جدید در Chrome باز شد. فرم‌های ویرایش و داده واقعی تغییر نکرده‌اند.

## سابقه: تبدیل واقعی لیست‌ها به AG Grid

کاربر تأکید کرد **لیست‌های فعلی هم باید AG Grid و مانند محصولات اورنزا باشند**. AG Grid Community 36.2.0 نصب و در lockfile تثبیت شد. کامپوننت مشترک و CSS/ترجمه مرکزی ساخته شدند و لیست هنرجویان، جلسات ترم، صورتحساب‌ها و دریافت‌های پرونده، کاربران، جلسات امروز، حضور معوق و تمدید داشبورد به آن متصل شدند. هیچ جدول HTML یا لیست دستی در این بخش‌ها باقی نمانده است. فرم‌ها و کارت‌های خلاصه ترم و داده واقعی حفظ شدند؛ بخش‌های جدید منو همچنان منتظر پیاده‌سازی جداگانه‌اند.

ظاهر خود grid از مرجع محصولات است: Material، دانا، RTL، رنگ زمینه/سرستون و حاشیه، ردیف ۵۶ و سرستون ۵۲، شماره ثابت راست، عملیات آیکونی ثابت چپ، فیلتر و مرتب‌سازی سرستون و صفحه‌بندی ۱۰/۲۵/۵۰/۱۰۰. در موبایل grid به کارت تبدیل نمی‌شود و پیمایش افقی و عملیات ثابت دارد. جزئیات فنی و مرجع در [LIST_UI_STANDARD.md](LIST_UI_STANDARD.md) ثبت شده‌اند. این تصمیم جای برنامه قبلی «تبدیل در آینده» را می‌گیرد.

API هنرجویان با حفظ قرارداد قبلی به دریافت بلوکی، فیلتر و مرتب‌سازی کل داده در SQLite گسترش یافت؛ نام ستون/عملگر/اندازه بلوک اعتبارسنجی و SQL پارامتری است. داده و مجوزها تغییر نکردند. صفحه و فیلترها پس از reload بازیابی می‌شوند. لیست‌های دیگر از مجموعه کامل مجاز پاسخ‌های قبلی استفاده می‌کنند. فقط تنظیمات ستون‌ها ذخیره می‌شوند، نه اطلاعات پرونده. هنگام بررسی، مسئله بازیابی صفحه پیش از دریافت تعداد کل و شکست نوار صفحه‌بندی موبایل رفع شد.

بررسی جاری: `npm run check` و production build موفق؛ initial برابر 797.85 kB و انتقال 138.04 kB، به‌علاوه chunk مشترک lazy AG Grid برابر ۱٫۱۴ MB خام / حدود ۲۵۸ kB انتقال. `npm test`: **۱۵ موفق**، شامل ۱۲۵ هنرجوی آزمایشی برای صحت sort/filter کل داده، صفحه دوم و بلوک دوم، حروف فارسی، فیلتر ترکیبی، wildcard و رد query نامعتبر. **Chrome نهایی: ۱۴ تست موفق در ۳۷٫۹ ثانیه، خروج صفر**. علاوه بر مسیر کامل و نقش‌ها، ۲۸ هنرجوی ساختگی برای بررسی صفحه‌بندی واقعی، بازگشت به صفحه دوم پس از reload، مرتب‌سازی صعودی کل داده، فیلتر ستونی و بازیابی فیلتر از URL آزمون شدند. ارتفاع ردیف/سرستون، عملیات ثابت و نبود سرریز کل صفحه در دسکتاپ و موبایل بررسی شدند. دو صورتحساب و یک دریافت واقعی در grid مالی، انتخاب ترم از اقدام «ثبت پرداخت»، فیلتر وضعیت «پرداخت جزئی» و لغو فرم بدون تغییر اطلاعات نیز تأیید شدند. فیلتر تاریخ از متن نمایشی شمسی استفاده می‌کند. تصاویر واقعی باز و اصلاح صفحه‌بندی موبایل تأیید شد: [لیست دسکتاپ](evidence/desktop-ag-grid.png)، [لیست موبایل](evidence/mobile-ag-grid.png)، [پرونده](evidence/desktop-profile.png)، [داشبورد](evidence/desktop-dashboard.png) و [کاربران](evidence/desktop-account.png)، [مالی دسکتاپ](evidence/desktop-finance.png) و [مالی موبایل](evidence/mobile-finance.png). همه داده تصاویر ساختگی و backend واقعی موقت است. سرور واقعی با همان دیتابیس برای بارگذاری کد جدید API راه‌اندازی مجدد شد؛ داده یا حساب بازنشانی نشده است.

بخش‌های زیر سابقه تحویل منو و بازطراحی قبلی‌اند؛ استاندارد جاری لیست‌ها همین بخش و LIST_UI_STANDARD.md است.

## سابقه تحویل: منوها و استاندارد اولیه لیست

کاربر خواست ابتدا منوهای کل دامنه ایجاد شوند و سپس بخش‌ها یکی‌یکی ساخته شوند. تمام لیست‌های جدید/بازسازی‌شده باید AG Grid با الگوی لیست محصولات اورنزا باشند؛ جزئیات فرم‌های ویرایش را کاربر برای هر بخش مشخص می‌کند. این قاعده در [LIST_UI_STANDARD.md](LIST_UI_STANDARD.md) و AGENTS.md ثبت شده است.

منوها مطابق بخش‌های ۱۳، ۱۷، ۱۹ و ۲۰ بریف: میز کار؛ آموزش (کلاس‌ها، ترم‌ها، جلسات)؛ مالی (صورتحساب، دریافت، بانک)؛ اطلاعات پایه (واحد آموزشی، آموزشگاه دیگر)؛ قوانین و مدارک؛ گزارش آموزشی/مالی؛ مدیریت (کاربر/نقش، تنظیمات، سربرگ، سابقه عملیات و حساب). منوهای هر نقش فقط در حد دسترسی فعلی نمایش داده می‌شوند و مقصدهای تازه route guard دارند.

۱۷ مقصد جدید فعلاً صفحه «در انتظار پیاده‌سازی» دارند، بدون فرم، لیست ساختگی یا API جدید. سه مسیر عملیاتی قبلی و فرم‌هایشان حفظ شده‌اند. منوی بلند اسکرول مستقل دارد تا مشخصات کاربر و برند در دسترس بمانند. هیچ لیست موجودی در این گام به AG Grid تبدیل نشده؛ نصب و اتصال کامپوننت مشترک آن با اولین لیست انتخاب‌شده انجام می‌شود.

بررسی این گام: `npm run check` و `npm run build` موفق؛ initial برابر 531.77 kB و انتقال تخمینی 103.70 kB. آزمون نهایی Chrome: **۱۲ تست موفق در ۳۳٫۴ ثانیه، خروج صفر**؛ تمام ۱۷ مقصد، هایلایت یکتای مسیر فعال، refresh مسیر، اسکرول منوی موبایل، محدودیت دسترسی منشی/حسابدار و ورود اجباری مستقیم بررسی شدند. چهار تست مسیر قبلی ثبت هنرجو تا تمدید و تاریخ نامعتبر نیز موفق ماندند. تصاویر [منوی دسکتاپ](evidence/desktop-menus.png) و [منوی موبایل](evidence/mobile-menus.png) باز و بصری بررسی شدند. جزئیات بازطراحی قبلی در بخش‌های زیر سابقه بررسی همان تحویل‌اند.

## تغییرات این بازطراحی

- پوسته: سایدبار تیره سمت راست با عرض ۲۶۵ پیکسل و حالت جمع‌شده ۸۴ پیکسل؛ هدر خلوت ۷۸ پیکسل، شناسه و نقش کاربر، عنوان، breadcrumb و نوار عملیات مشترک. منوی موبایل با backdrop، Escape، بازگرداندن فوکوس، چرخه Tab و جلوگیری از اسکرول پس‌زمینه.
- داشبورد: شمارنده‌های واقعی هنرجوی فعال، جلسات امروز، حضور معوق و تمدید؛ ساعت تهران و لینک مستقیم حضور؛ جدول ترم با یک جلسه باقی‌مانده یا تکمیل‌شده بدون تمدید؛ بدهی واقعی به تفکیک ارز و مسیر ورود به پرونده برای دریافت. مبلغ بدهی جمعی است؛ گزارش تفصیلی بدهکاران و فیلتر مالی جدید در این تغییر اضافه نشده‌اند.
- هنرجویان: toolbar ثبت، فرم ثبت سریع، جست‌وجو و فیلتر، ردیف دارای هویت هنرجو، شماره با جهت صحیح، badge ظریف و عملیات کوچک؛ صفحه‌بندی و وضعیت جست‌وجوی URL حفظ شده‌اند. در موبایل هر ردیف تمام اطلاعات و دکمه پرونده را زیر هم نشان می‌دهد.
- الگوی مشترک به پرونده، ترم/تمدید، دریافت، جلسه، حضور و غیاب، ورود و حساب/دسترسی‌ها اعمال شد: دانا، آیکون SVG خطی مستقل، پس‌زمینه خنثی، کارت سفید، شعاع ۶–۷ پیکسل، حاشیه ظریف، فاصله‌های منظم و سایه محدود. فونت دانا همان پنج فایل محلی قبلی است.
- Floating Label واقعی داخل کادر؛ عنوان پس از فوکوس/مقدار بالای مقدار می‌رود. select/زمان عنوان ثابت بالا دارند؛ صفر و select غیرفعال تمدید بررسی شده‌اند. خطا بیرون فضای مقدار است.
- API، پاسخ‌های مجاز هر نقش، منطق مالی/آموزشی و دیتابیس واقعی تغییر نکرده‌اند. هیچ seed یا reset روی اطلاعات واقعی انجام نشده است.

## قابلیت‌های خروجی اول

- Angular 22.2.3 standalone، strict، lazy routes و Reactive Forms؛ zoneless/OnPush با اعلان تغییر پس از پاسخ async. Node 24.16، Express و SQLite واقعی با foreign keys، WAL و تراکنش؛ مهاجرت idempotent و بدون نمونه‌سازی خودکار.
- ورود scrypt، نشست HttpOnly/SameSite، CSRF و Origin، rate limit، خروج/تغییر رمز، قطع نشست کاربر غیرفعال، حفاظت آخرین مدیر؛ مدیر اولیه و بازیابی از CLI.
- ثبت هنرجو/سرپرست مشترک، کد خودکار، جست‌وجوی نرمال‌شده فارسی و صفحه‌بندی سرور؛ انتخاب واحد موردنظر، ترم یا صورتحساب خودکار نمی‌سازد.
- مسیر کامل خصوصی: ترم با سهم قابل تنظیم، صورتحساب مستقل، تومان/دلار با مبلغ صحیح، دریافت و تخصیص جدا، اعتبار اضافه و idempotency اتمیک؛ رزرو و ویرایش زمان با ظرفیت/نسخه؛ حضور، غیبت با انتخاب مصرف، کنسلی با عامل/دلیل و جایگزین؛ تکمیل/بازگشایی آموزشی؛ تمدید بدون کپی جلسه/پرداخت و با حفظ بدهی قبلی.
- نقش منشی داده مالی نمی‌گیرد و حسابدار داده آموزشی غیرضروری نمی‌گیرد. تمام کنترل‌ها در سرور برقرارند.

## روش اجرا

```sh
APP_ORIGIN=http://localhost:3000 npm run api
```

آدرس: http://localhost:3000 — در این اجرا سرور فعال و نسخه جدید در Chrome باز شد. اگر shell قدیمی service worker دیده شد، برای پیش‌نمایش از http://localhost:3000/?ngsw-bypass=true استفاده کنید. حساب و داده موجود حفظ شده‌اند.

برای نصب تازه: `npm ci`، کپی `.env.example` به `.env`، `npm run migrate`، ساخت مدیر با رمز محیطی طبق [README](../README.md)، سپس `npm run build` و فرمان بالا. توسعه با دو ترمینال `npm run api` و `npm start` روی localhost:4200 و APP_ORIGIN متناسب. نمونه‌سازی فقط صریح با `npm run seed -- --demo` روی دیتابیس خالی؛ روی دیتابیس واقعی اجرا نشود. بکاپ با `npm run backup -- /absolute/path/backup.sqlite`.

## کارهای باقی‌مانده

- مطابق مراحل بعد بخش ۱۹: آموزش گروهی/چندمسیره و انتقال افتتاحیه دفتر؛ مدیریت حساب بانکی/اعتبار، اصلاح/ابطال مالی و رسید؛ مجوزهای جزئی؛ قوانین و مدارک؛ PDF سربرگ و گزارش شمسی/CSV و داشبورد تحلیلی.
- گزارش تفصیلی بدهکاران و فیلترهای مالی، مستقل از جمع بدهی و مسیر پرونده موجود، در مرحله گزارش‌ها تکمیل می‌شود.
- PWA نهایی: نصب/آپدیت و offline، آیکون‌های استاندارد و maskable، کش، autofill، بزرگ‌نمایی و صفحه‌کلید روی دستگاه‌های فیزیکی؛ shell-only service worker و manifest موجودند.
- استقرار عمومی انجام نشده؛ SQLite فعلی برای تک‌نمونه است. چندنمونه نیازمند PostgreSQL است.

نبود بسته اصلی Metronic مانع این بازطراحی نیست و درخواست دریافت آن برای این مرحله مطرح نیست.
